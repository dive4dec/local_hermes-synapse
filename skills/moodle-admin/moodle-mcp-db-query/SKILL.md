# Moodle MCP DB Query (read-only SQL)

Read-only SQL access to the Moodle database via the `moodle_db` MCP server. Complements the manually-authored `moodle-db-access` skill (PHP bootstrap, which is still required for **writes**).

## Triggers

- Any read-only lookup: course activities, quizzes, forums, groups, enrolments, questions
- Quick verification of DB state before/after a change
- (Historical note: the `moodle-db-access` skill once claimed "no general query tool exists" — outdated. The MCP query tool works; verified again 2026-08-27. Use it for reads; use PHP bootstrap for writes or when the keyword filter blocks you.)

## Tools

- `mcp__moodle_db__query` — `SELECT` / `SHOW` / `DESCRIBE` only; 100-row limit; sensitive columns redacted
- `mcp__moodle_db__list_tables` — all tables + row counts
- `mcp__moodle_db__describe_table` / `schema_hints` — schema discovery

## Resolving activity display names

`mdl_course_modules` has **no `name` column** in this install (Moodle 5.x; there is no `mdl_course_modules_name` table). Get names from the instance table:

```sql
-- module name from mdl_modules (cm.module = m.id), instance name from the module's table
SELECT cm.id AS cmid, m.name AS modulename, q.name AS instancename
FROM mdl_course_modules cm
JOIN mdl_modules m ON m.id = cm.module
JOIN mdl_quiz q ON q.id = cm.instance
WHERE cm.course = 3 AND cm.module = 4;  -- 4 = numeric module id (choice); see pitfall 11
```

## Pitfalls (verified on this site)

1. **Naive substring keyword filter:** SELECTing any column whose *name* contains a dangerous word rejects the whole query — `deleted` or `userdeleted` → "dangerous keyword (DELETE)", `created` (e.g. `mdl_forum_posts.created`) or `timecreated` → "dangerous keyword (CREATE)", `needsupdate` (e.g. `mdl_grade_items.needsupdate`) → "dangerous keyword (UPDATE)" (verified 2026-08-27), `alternatename` (e.g. `mdl_user.alternatename`) → "dangerous keyword (ALTER)" (verified 2026-09-10). **The SQL function `REPLACE()` is also rejected** (contains "REPLACE" → dangerous, verified 2026-08-28) — so the classic count trick `(LENGTH(x)-LENGTH(REPLACE(x,'s','')))/n` won't run here; do the counting in the PHP bootstrap instead. Workaround: drop the offending column, or run that one query via the PHP bootstrap. **Better: `SELECT *`** — the guard scans the query *text* (the column names you write in the SELECT list), not the returned rows, so `SELECT * ...` passes and the blocked columns (`timecreated`, `updated`, `created`, `deleted`, ...) still come back in the result set. To sort by a blocked timestamp use `ORDER BY id` (row ids are insertion-ordered ≈ chronological) instead of `ORDER BY timecreated` (verified 2026-09-10: `SELECT * FROM mdl_logstore_standard_log WHERE objecttable='user' AND objectid=618 ORDER BY id DESC` returned `timecreated` values fine; the same fetch with `timecreated` named explicitly, or with `ORDER BY timecreated`, was rejected). Note `mdl_user` has **both a `created` and an `updated` column** — each independently trips the filter, so a `SELECT id, email, created, updated` is blocked on both and must be `SELECT *`. **The guard also scans string LITERALS:** a dangerous word inside a *value* is rejected — `eventname IN ('attempt_updated')` → "dangerous keyword (UPDATE)" (verified 2026-10-06). Eventname lists via this tool must avoid any literal containing UPDATE/DELETE/CREATE/ALTER/REPLACE; use `eventname LIKE '%attempt%'` (no dangerous substring) or take that query to the PHP route.
2. **100-row cap:** aggregate (`COUNT`, `GROUP BY`) or paginate with `ORDER BY ... LIMIT/OFFSET`.
3. **`mdl_forum_discussions.name` is the discussion title** — there is no `subject` column.
4. **Forum column names are not the obvious ones (verified via `SHOW COLUMNS`):** `mdl_forum_discussions.forum` (NOT `forumid`), `mdl_forum_posts.discussion` (NOT `discussionid`); thread replies link via `mdl_forum_posts.parent`. To resolve a `mod/forum/discuss.php?d=N#pM` URL: `N` = `mdl_forum_discussions.id`, `M` = `mdl_forum_posts.id`. Pull all posts of a discussion with `WHERE p.discussion = N ORDER BY p.id` (also fetch `messagetrust`/`messageformat` — format 4 = markdown; `firstpost` column on the discussion row is the top post id). Recency: `mdl_forum_discussions.timemodified` is selectable, but posts' `created`/`deleted` columns are blocked by the keyword filter (pitfall 1). **`mdl_forum_discussions` itself has NO `created` column** (full column set: `id,course,forum,name,firstpost,userid,groupid,assessed,timemodified,usermodified,timestart,timeend,pinned,timelocked`) — `ORDER BY created` or `$DB->get_records('forum_discussions', [...], 'created ASC')` fails with a swallowed "Error reading from database" (verified 2026-09-05); sort discussions by `timemodified` instead.
   **`mdl_forum_subscriptions` has neither `discussion` nor `forum` columns** (verified `SHOW COLUMNS` 2026-08-23 — only `id, userid, forum, preference`); the subscription is per-user-per-forum, not per-discussion.
   **The forum discussion LIST page query** (from `mod/forum/lib.php::forum_get_discussions()`): `SELECT ... FROM mdl_forum_discussions d JOIN mdl_forum_posts p ON p.discussion = d.id JOIN mdl_user u ON p.userid = u.id WHERE d.forum = ? AND p.parent = 0` (+ timed-post/group filters). Running that join read-only via this tool is the fast way to confirm which discussions a user will actually see in the listing — useful for verifying forum content changes (with `groupmode = 0` on the forum's CM, the join result == the UI listing).
5. **`mdl_forum` lacks `mandatorysubscribe`, `displaydays`, `forummode`, and `displayorder`** here (Unknown column). The real columns (verified via `SHOW COLUMNS`, Moodle 5.x) are: `id, course, type, name, intro, introformat, duedate, cutoffdate, assessed, maxbytes, maxattachments, forcesubscribe, trackingtype, rsstype, rssarticles, timemodified, warnafter, blockafter, blockperiod, completiondiscussions, completionreplies, completionposts, displaywordcount, lockdiscussionafter, showimmediately`. For forum type use `type` — values seen live on this site (verified 2026-09-05): `general`, `qanda` (the live Q&A style), `news` (announcements), and legacy **`qa`** (old-format Q&A that survives as dead duplicate forums — course <cid> has three empty `qa` "CE-Quiz FAQ" forums, ids 7/8/10, beside the live `qanda` id 11).
6. **`mdl_course_sections.sequence` is the display-order comma list of CM ids** — useful to reconstruct a section. It can contain dangling CM ids after an activity is deleted without resequencing; harmless for rendering, clean up on next resequence.
7. **`mdl_context` levels (verified by query 2026-08-27):** course context = `contextlevel = 50` (`CONTEXT_COURSE`) AND `instanceid = <courseid>` (no `courseid` column); **70 = module** (e.g. a quiz's contextid resolves via `instanceid=<cmid>, contextlevel=70`). Role assignments for a course use the level-50 context. (The `moodle-db-access` skill's note "contextlevel=70 = course" is WRONG for this install — do not copy it.)
8. **Site is served under a sub-path:** `$CFG->wwwroot = https://<moodle-host>/<course-code>` (verified 2026-08-27). Moodle-absolute URLs must include the `/<course-code>` prefix — bare `https://<moodle-host>/course/view.php?id=N` 404s (curl-verified). When validating links found in course content, prepend the base path; relative links like `../mod/resource/view.php?id=97` are fine.
9. **Moodle 5.x singular instance tables (verified 2026-08-27):** `mdl_label`, `mdl_page`, `mdl_resource`, `mdl_url`, `mdl_wiki`, `mdl_assign` — the old plural names (`mdl_labels`, `mdl_pages`, ...) → "Table does not exist". Instance rows store the description in `intro`/`introformat` (page adds `content`/`contentformat`). Verified 5.x column renames: `mdl_url` has `externalurl` (no `url`); `mdl_page` has no `subpages`; `mdl_resource` has no `content`/`displaylines`; `mdl_label` has no `section` (section lives on the CM) and its body text is in **`intro`**/**`introformat`** (NOT `content` — `SELECT l.content` → Unknown column; only 6 columns: `id,course,name,intro,introformat,timemodified`, verified 2026-09-02); `mdl_groups` has `visibility` and the course FK is **`courseid`** (no `course`/`visible` columns — verified 2026-08-29: `WHERE g.course = 3` fails with Unknown column); `mdl_quiz_overrides` has `quiz, groupid, userid, timeopen, timeclose, timelimit, attempts, password` and **no `preventlate`** (preventlate is on `mdl_quiz`); `mdl_role_assignments` has **no `groupid`** — course-scoped roles use `component='core', itemid=<courseid>`; `mdl_user` has no `siteadmin` column (site admin = `is_siteadmin()` in PHP); `mdl_capabilities` is plural; `mdl_role_capabilities` stores the capability as a `capability` **string** column (no `capabilityid`).
10. **Capability renames in 5.x:** activity deletion is `moodle/course:delete` (NOT the older `moodle/course:deleteactivity` — the old name resolves to "capability not found" → has_capability false, even for the site admin).
11. **`mdl_course_modules.module` is the NUMERIC FK into `mdl_modules.id` — not the module name** (verified 2026-08-27: `WHERE module='quiz'` silently returns 0 rows — nearly caused the false conclusion that a quiz had no CM at all). Module ids on this site: quiz=17, label=12, lti=14, page=15, qbank=16, resource=18, forum=8, url=21, wiki=22, assign=1, feedback=6, subsection=20, choicegroup=24. Join `mdl_modules` for names; filter by numeric id. There is also **no `mod` or `modname` column** — `WHERE c.mod='quiz'` → Unknown column 'c.mod' (2026-10-12).
12. **More 5.x schema quirks (verified by live queries 2026-08-27):** `mdl_quiz` has **no `maxgrade` / `sumattempts` / `canattempt`** — the quiz's max grade is the `grade` column (other columns incl. `attempts`, `timeopen`, `timeclose`, `preventlate`). `mdl_grade_categories` has **no `name`** (use `fullname`) and **no `itemtype`/`itemmodule`/`iteminstance`** (categories aren't items; item linkage lives on `mdl_grade_items`). The classic question↔quiz join table `mdl_quiz_questions` **does not exist** in this install — confirm the real name via `list_tables` before summing quiz question marks.
13. **`mcp__moodle_db__describe_table` takes a `table` parameter** (passing `table_name` fails validation).
14. **More 5.x schema traps (verified 2026-08-28):** `mdl_question` has **no `category` column** — the category FK is named **`parent`** (`mdl_question.parent` → `mdl_question_categories.id`); `WHERE category = 57` fails with a swallowed "Error reading from database" (Moodle's dml_read_exception hides the real error — test a simple variant first). `mdl_course` has **no `deleted` column** — courses are hard-deleted; `WHERE deleted = 0` errors (38 columns, no deleted). `mdl_post` (legacy, empty in 5.x) text column is **`content`** (no `message`/`fullmessage`); forum filtering = `module='forum'` + `courseid`. **`mdl_forum_posts` text column is `message`** (NOT `content` — `SELECT .../WHERE content` → Unknown column, verified 2026-09-10; full set: `id, discussion, parent, userid, created, modified, mailed, subject, message, messageformat, messagetrust, attachment, totalscore, mailnow, deleted, privatereplyto, wordcount, charcount`; note `created`/`deleted` are keyword-blocked in WHERE/SELECT lists). `mdl_course` has **no `categoryid` / `enrolledusers`** (category FK = singular `category`; enrolled counts must be computed from `mdl_user_enrolments`). `mdl_page` has **no `subintro`** (just `intro`/`content`).
15. **`cm.instance` ids are per-module, not globally unique:** `WHERE cm.instance IN (10,11,12)` without a `cm.module = <id>` filter silently matches unrelated modules with colliding ids (verified 2026-08-28: phantom page rows from course 2). Always filter by `cm.module` (numeric, pitfall 11) when resolving instance rows from CM ids — or join as `cm.instance = t.id AND cm.module = (SELECT id FROM mdl_modules WHERE name='<mod>')`.
16. **`mdl_question_usages` is the per-activity question-usage table in this Moodle 5.x** (no `mdl_questions_usage_by_activity` — that name doesn't exist). Its `id` column == the `uniqueid` of the attempt/usage (i.e. `mdl_quiz_attempts.uniqueid` for quiz attempts); other columns: `contextid, component, preferredbehaviour`. (Verified 2026-08-29.)
17. **`moosh user-delete` = `user_delete_user()` = SOFT delete (Moodle 5.x `delete_user()`):** the `mdl_user` row is NOT removed. It sets `deleted=1`, renames the username to `email.<10-digit timestamp>` (truncated to 100 chars), MD5-hashes the email, clears idnumber, and strips enrolments/roles/groups/grades/completions/preferences. **It does NOT delete `mdl_quiz_attempts`, `mdl_quiz_grades` (for quizzes where attempts remain), `mdl_logstore_standard_log`, or `mdl_question_usages`.** To fully purge a user's quiz history afterwards: call `quiz_delete_attempt($attemptid, $quiz)` (mod/quiz/locallib.php — requires the quiz object to have a `cmid` or it resolves one; it also removes the question usages and recomputes/deletes `mdl_quiz_grades`). Never verify the soft-delete via `timeupdated` (column doesn't exist) — use `timemodified`/`timecreated`.
18. **Enrolment / grade / LTI / user column names (verified 2026-08-28):** `mdl_user_enrolments` FK to `mdl_enrol.id` is **`enrolid`** (NOT `enrolment`); `mdl_grade_grades` has **no `courseid`** (scope via `mdl_grade_items` joins); `mdl_user` has a **`deleted`** column (soft-deleted users: `deleted=1`, username anonymized to `email.<timestamp>`, email MD5-hashed — always filter `u.deleted=0` in roster queries); LTI enrol tables are `mdl_enrol_lti_users` (`userid`, `toolid`, `consumerkey`, `sourceid`) and `mdl_enrol_lti_user_resource_link` (keys on **`ltiuserid`** = `mdl_enrol_lti_users.id`, NOT `userid`). Completion tracking = `mdl_course_completions` + `mdl_course_modules_completion` (no `mdl_completion_state`/`mdl_completion_trackdata`). Tables that do NOT exist here: `mdl_quiz_steps`, `mdl_quiz_questionstate`, `mdl_lti_launches`, `mdl_wiki_subpages`, `mdl_forum_discussion_posts`.
19. **MCP `query` tool parameter is named `query`** (not `sql`) — passing `sql` fails validation with "Field required: query".
20. **Calendar events / enrolments / completion columns (verified 2026-08-29):** `mdl_event` (5.x) columns: `id,name,description,format,categoryid,courseid,groupid,userid,repeatid,component,modulename,instance,type,eventtype,timestart,timeduration,timesort,visible,uuid,sequence,timemodified,subscriptionid,priority,location` — course filter is **`courseid`** (no `course` column), the activity FK is **`instance`** with module type in `modulename` (no `cmid`/`quiz` column), times are **`timestart`**/**`timeduration`** (no `startdate`/`enddate`); quiz opens/closes = `type` 0/1. `mdl_event.description` holds a **pre-rendered snapshot** of the activity intro (with autolinks already resolved) — it does NOT update when the activity's intro is edited in the DB; regenerate with `quiz_refresh_events()` (see `moodle-course-maintenance` → `references/calendar-event-sync.md`). **`mdl_user_enrolments` has NO `courseid`** (`id,status,enrolid,userid,timestart,timeend,modifierid,timecreated,timemodified`) — course-scoped queries must join through `mdl_enrol`:

```sql
-- enrolled-student count for a course (5.x): role must sit on the level-50 course context
SELECT COUNT(DISTINCT ue.userid)
FROM mdl_user_enrolments ue
JOIN mdl_enrol e ON e.id = ue.enrolid
JOIN mdl_role_assignments ra ON ra.userid = ue.userid
JOIN mdl_role r ON r.id = ra.roleid
JOIN mdl_context c ON c.id = ra.contextid AND c.contextlevel = 50 AND c.instanceid = <courseid>
WHERE e.courseid = <courseid> AND r.shortname = 'student' AND ue.status = 0;
```

`mdl_course_modules_completion` columns: `id,coursemoduleid,userid,completionstate,overrideby,timemodified` — the FK is **`coursemoduleid`** (not `coursemodule`); completed-count = `WHERE coursemoduleid = <cmid> AND completionstate = 1`. Caveat: with manual tracking (`course_modules.completion = 1`) this counts only self-declared "mark as done" clicks, and can include auto-provisioned LTI accounts (username `enrol_lticc...`) — cross-check against the enrolled-student roster before quoting the number as "students who did X".
   **`mdl_course_modules.completion` enum:** 0 = tracking disabled, 1 = manual (user must click "mark complete"), 2 = automatic (activity criteria, e.g. pass a quiz / view a page). "Required reading" tasks in <course> courses are usually a **label** in the topic section whose `intro` has a `Reading` heading + link into the courseware resource (see `references/<coursecode>-26a-course-map.md` for course <cid>'s per-topic layout); find it via `mdl_label.id = cm.instance` joined on `cm.module = 12`. Because manual tracking is self-declared, the completion count **undercounts** actual readers — for a readership estimate, count page views of the resource page in `mdl_logstore_standard_log` instead (or offer both numbers).
21. **`rows` and `usage` are reserved words in this MariaDB:** `COUNT(*) AS rows` fails with a syntax error ("...near 'rows FROM ...'"); same for `SELECT a.uniqueid AS usage` ("...near 'usage, ...'") — both bit 2026-09-24. Use different aliases (e.g. `usercount`, `cnt`, `us`, `usid`).
22. **LTI group-sync roster (the "ltigroups" plugin):** `mdl_ltigroups_roster` = `id, courseid, eid, assignments, userid, timesynced, timecreated`. One row per student in the external group-sync source; `eid` = CityU email, `assignments` = JSON like `{"Lec":"C01","Lab":"T01"}`, and **`userid` is NULL = never launched an LTI activity** (Moodle auto-provisions an `enrol_lti<hash>` account on first notebook launch — that is what "logged in" means here). Config in `mdl_ltigroups_config` (`courseid, joinkey, staged`), column→grouping mapping in `mdl_ltigroups_mapping` (`courseid, groupingname, csvcolumn, sortorder`). To list "roster students not yet enrolled": `WHERE courseid = <cid> AND (userid IS NULL OR userid = 0)`. Watch for test rows in the roster — course <cid> carries `e_lti_test0@<domain>` (C01/T02), `e_lti_test3@<domain>` (C01/T03), `e_lti_test1@<domain>` (CA1/TA1); some already have accounts, so exclude emails like `e_%e_lti_test@<domain>` from "not enrolled" counts. (Verified 2026-09-02: course <cid> = 212 roster rows, 177 linked.)
23. **Text-filter state tables were renamed in this Moodle 5.x:** `mdl_filters` does NOT exist (Unknown table) — filter enable/disable state is **`mdl_filter_active`** = `id, filter, contextid, active, sortorder` (column is `filter` holding the plugin *name* e.g. `urltolink`, not `pluginname`/`activepluginid`), config is `mdl_filter_config` = `id, filter, contextid, name, value`. `contextid = 1` (system context) = site-wide default; a row at the activity's **module context** (level 70, `contextid` = CM id) = per-activity override; **no row = inherit**. `active` values: `1` = ON, `0` = INHERIT, `-1` = OFF, `-9999` = DISABLED (constants `TEXTFILTER_ON/INHERIT/OFF/DISABLED` in lib/filterlib.php). The site-wide row for a filter that is simply on inherits no override anywhere — check `contextid=1` first. Per-activity overrides do exist in the wild (other courses' quizzes carry `activitynames:-1` rows), so this is a normal mechanism. **"Convert URLs into links and images" = filter `urltolink`**; the activity-name autolinker is filter `activitynames` (different filter — disabling urltolink does not touch activity autolinks). Set state via the standard function `filter_set_local_state($filter, $contextid, TEXTFILTER_OFF)` (lib/filterlib.php:395) rather than hand-inserting rows; state `TEXTFILTER_INHERIT` deletes the row. UI equivalent: the activity's Preferences → "Text filters" checkboxes. (Verified 2026-09-02.) To JOIN override rows to activity names: `JOIN mdl_context c ON c.id = fa.contextid AND c.contextlevel = 70` then `JOIN mdl_course_modules cm ON cm.id = c.instanceid` (module contexts key on the CM id via `instanceid`), and filter `fa.contextid = 1` = system row separately. (Verified 2026-09-05.)
 24. **Students without a group (recurring query):** "list students not assigned any group" = enrolled students with no row in `mdl_groups_members` (optionally scoped to the course's groups via `mdl_groups.courseid`). Gotcha: a student with multiple enrolment methods (manual + LTI, etc.) produces MULTIPLE `mdl_user_enrolments` rows, so counting rows double-counts (verified 2026-09-04: 381 rows for 182 distinct students in course <cid>) — always `COUNT(DISTINCT u.id)` / `COUNT(DISTINCT CASE WHEN ... THEN u.id END)`, or collapse via a subquery `WHERE u.id IN (...)`. A LEFT JOIN through `mdl_groups_members` then `LEFT JOIN mdl_groups g ON g.id = gm.groupid AND g.courseid = <cid>` with `gm.userid IS NULL` finds the ungrouped. Expect test accounts in the result (`Test Student` enrol-lti@example.com, LTI test users) — flag them separately from real students.
   **Reporting a student's specific group (e.g. "which Lab group"):** `mdl_groups_members` is a pure user↔group table with **no grouping column** — a student is in several groups at once (course <cid>: one `Lec` + one `Lab` + optionally a `project`). To say which is their *lab* group you must map group→grouping via `mdl_groupings_groups` (join `mdl_groupings` for the name). **Do NOT infer it by name pattern alone** (e.g. "T0x/TA1 = lab") — in this course the *project* groups are the `groupNN` names and helpers sit in the **Lec** grouping (group <helpergid> "helpers" is grouping `Lec`, not `Lab`), so name-guessing mislabels them. Also: a student's `project` group is **self-registered** in the Project choicegroup (topic 105), NOT part of LTI sync — don't attribute project membership to the group-sync plugin.
25. **Role capability lookups (verified 2026-09-10):** capability strings carry the `moodle/user:` prefix — querying `user/editownprofile` (missing prefix) in `mdl_role_capabilities` matches **0 rows** and looks exactly like "no prohibition exists" (nearly caused a false "the Prohibit was never set" conclusion). Query the full string `moodle/user:editownprofile`. This install's `permission` integers are **NOT** the textbook 0/1/2/3: observed **`-1000` = PROHIBIT, `1` = ALLOW** (system context: role `user`(7)=-1000, `guest`(6)=-1000, `manager`(1)=1). There is **no `authenticated` role** in this install — the base role every authenticated user holds is `user` (id 7). `mdl_user_role_rules` (per-user capability overrides) **does not exist** here (MCP: "Table doesn't exist"; PHP: swallowed "Error reading from database").
26. **String-enum vs integer comparison silently miscounts (verified 2026-09-14):** `mdl_quiz_attempts.state` is a **string** enum (`inprogress`/`finished`/`aborted`). Comparing it to an integer — `SUM(state = 0)`, `WHERE state = 1`, or `CAST(state AS UNSIGNED) GROUP BY state` — is wrong: MySQL coerces each non-numeric string to `0`, so `state = 0` is TRUE for **every** row (a quiz that was 8 finished + 1 in progress reported as "9 of 9 in progress") and the CAST collapses all states into a single `0` group. Always quote enum values: `state = 'inprogress'` / `'finished'` / `'aborted'`. The trap applies to any string column compared against an integer literal.
27. **Question-engine join gotchas (verified live 2026-09-14, CE-Quiz 1, quiz 58):**
    - **"Question N" ≠ `mdl_question_attempts.slot = N`.** Slot 1 is often an "Information" description page (`maxmark = 0`, `mdl_question.name = 'Information'`), so Question 1 sits at slot 2. Filtering `qs.slot = 1` returns zero real rows. Resolve by listing slots first — `SELECT qs.slot, q.id, q.name, qs.maxmark FROM ... GROUP BY qs.slot, q.id, q.name, qs.maxmark ORDER BY qs.slot` — and picking the Nth slot with `maxmark > 0`.
    - **Group-join fan-out in per-student reports.** <course> students sit in 2–3 groups at once (Lec `C01`/`CA1` + Lab `T0x`/`TA1` + project `groupNN`), so joining `mdl_groups_members` × `mdl_groups` on top of an attempt join multiplies rows (39 in-progress students → 101 rows). Dedupe with `GROUP BY qa.id, u.id, ...` (or `COUNT(DISTINCT ...)`) or filter to the lab group id/name when one row per student is wanted. Never treat raw row count from a group-joined per-student query as a student count.
    - **`mdl_question_attempt_steps.state = 'todo'` is NOT always "never touched".** A step with `mdl_question_attempt_step_data` row `-_precheck = 1` and **no** `-_rawfraction` row is a Check-button-only run (precheck, not graded). Reading live progress: `todo` + several precheck steps = actively working; `todo` + `-_rawfraction 0` rows = submitted and failed; state `complete`/`gradedright` = passed. (`-submit`, `-_try`, `-_rawfraction` are the other useful step-data keys.)
28. **Code Runner question definitions (verified 2026-09-14, course <cid> <course> questions):**
    - **Per-test rows live in `mdl_question_coderunner_tests`** (NOT in the options table): `questionid, testtype, testcode, stdin, expected, extra, useasexample, display, hiderestiffail, mark`. `useasexample=1` = the visible "Check" example test; `useasexample=0` = hidden graded tests; `display` = `SHOW`/`HIDE` controls what students see on failure. This is the authoritative way to see what a question actually grades — the stem (`mdl_question.questiontext`) can REQUIRE things (e.g. "store the input in a variable named `domain`") that only hidden tests enforce (`testcode = assert domain == "..."`), while the visible example test checks stdout only.
    - **`mdl_question_coderunner_options`** columns: `questionid, coderunnertype, precheck, allornothing, answer, globalextra, penaltyregime, ...`. `answer` = the model solution (not the tests — `globalextra` is empty and there is no `template` column here); **`penaltyregime`** is the adaptive-behaviour penalty schedule, e.g. `"10, 20, ..."` = each wrong submit multiplies the raw fraction by 0.9, 0.8, … (a trailing `...` repeats the last two as an arithmetic series). All <course> questions use `penaltyregime "10, 20, ..."` + `coderunnertype python3_<course>_prototype`.
    - **Final displayed fraction vs raw fraction:** `mdl_question_attempt_steps.fraction` is the ADJUSTED mark (best raw fraction across submits × penalty for tries consumed); the submit's raw value is the step-data key `-_rawfraction`. So `fraction = 0.9` + `_rawfraction = 1` = solved on the 2nd submit, 10% penalty — NOT a partial answer. Behaviour source: `<webroot>/question/behaviour/adaptive_adapted_for_coderunner/behaviour.php` (`adjusted_fraction()`).
    - **Per-attempt, per-question trail:** `mdl_question_attempts` (`questionusageid`, `slot`, `questionid`, `maxmark`) → `mdl_question_attempt_steps` (`sequencenumber`, `state`, `fraction`) → `mdl_question_attempt_step_data` (`attemptstepid`, `name`, `value`). Student code per submit = the `answer` key; per-test results = the PHP-serialized `_testoutcome` key (grep for `NameError`/`***Run error***`).

29. **Get a quiz's actual questions (verified working join, 2026-09-21):** a quiz has no `questionid` anywhere on its CM/quiz row. The chain is `mdl_quiz_slots` → `mdl_question_references` → `mdl_question_versions` → `mdl_question`:

    ```sql
    SELECT s.slot, s.maxmark, qv.questionid, q.name, q.qtype
    FROM mdl_quiz_slots s
    JOIN mdl_question_references qr ON qr.itemid = s.id AND qr.component = 'mod_quiz'
    JOIN mdl_question_versions qv ON qv.questionbankentryid = qr.questionbankentryid AND qv.version = qr.version
    JOIN mdl_question q ON q.id = qv.questionid
    WHERE s.quizid = <quizid> ORDER BY s.slot;
    ```

    - Full text is in `mdl_question.questiontext` — fetch it in a follow-up for the returned `questionid`s (it's long; the 100-row cap + big text would truncate otherwise). Count cross-check first: `SELECT COUNT(*) FROM mdl_quiz_slots WHERE quizid = <quizid>`.
    - **Read the schema from `information_schema` first — do NOT guess column names** (I burned ~15 queries on non-existent ones). Verified shapes: `mdl_quiz_slots` = `id, slot, quizid, page, displaynumber, requireprevious, maxmark, quizgradeitemid` (**no `questionid`, no `sectionid`**). `mdl_quiz_sections` = `id, quizid, firstslot, heading, shufflequestions` (heading groupings only, **no question column**). `mdl_question_references` = `id, usingcontextid, component, questionarea, itemid, questionbankentryid, version`; for quiz slots `component='mod_quiz'`, `questionarea='slot'` (singular), `itemid = mdl_quiz_slots.id`. `mdl_question_versions` = `id, questionbankentryid, version, questionid, status`.
    - The join anchor is the reference's **`questionbankentryid`**, not `mdl_question.id` — never `JOIN mdl_question q ON q.id = qr.itemid`.
    - Tables that **do NOT exist** here (do not join): `mdl_question_questions_usage`, `mdl_quiz_questions` (the latter already noted in pitfall 12).
    - Course 3 quirk: the section **named** "Midterm Quiz" (section 13) is **empty**; the real Midterm / Midterm (makeup) / 7 Mock Midterms live in a later **unnamed** section (their CM rows carry a section value with no matching `mdl_course_sections` row — topic order is driven by the CM rows). Don't conclude "the midterm section has no quizzes" from the named section being empty.

30. **Question-engine step tables: exact columns + manual-grade authorship (verified `SHOW COLUMNS` 2026-09-24):** `mdl_question_attempt_steps` = `id, questionattemptid, sequencenumber, state, fraction, timecreated, userid` — **NO `name` column** (selecting it → "Unknown column 's.name'", and via PHP a swallowed "Error reading from database"). `mdl_question_attempt_step_data` = `id, attemptstepid, name, value` — **NO `userid`, NO `timecreated`** (those live on the parent step row). FK: `step_data.attemptstepid` → `steps.id` → `steps.questionattemptid` → `question_attempts.id`. Manual per-question grading (the "Edit comment or grade" popup) appends a step whose `state='mangrwrong'` (or `mangr...`) with `steps.userid` = grader (admin 2) and step_data rows `-mark`, `-maxmark`, `-comment`, `-commentformat`; a student's own submission mark is a step with `steps.userid` = the student — so "who applied this mark" is decided by `steps.userid`, not by the mark value. Worked example (MCP, 16-slot zero-out): `SELECT s.questionattemptid, s.id, s.userid, s.state, d.name, d.value FROM mdl_question_attempt_steps s JOIN mdl_question_attempt_step_data d ON d.attemptstepid=s.id WHERE s.questionattemptid IN (SELECT id FROM mdl_question_attempts WHERE questionusageid=<uniqueid> AND slot>1) AND d.name IN ('-mark','-comment')` → expect one `-mark` + one `-comment` row per question attempt. (`timecreated` is keyword-blocked in the text — "CREATE" — so don't name it; use `sequencenumber`/`ORDER BY id` for ordering.)
31. **Swallowed "!!! First response: `SHOW COLUMNS FROM <table>` through this MCP tool (or fetch one row and print `array_keys` in PHP), then re-query with real columns. Do NOT retry the same query, and do NOT conclude the data is missing. Also: the same nested-`IN (SELECT … IN (SELECT …))` count that works here can die with a bare error inside the PHP bootstrap (get_records_sql flakiness) — prefer this tool for final question-engine verification.
32. **Per-question final grade + student code (verified 2026-10-06, u553 on CE‑Quiz 4):** `mdl_question_attempts.maxfraction` is **NOT** a reliable per‑question grade — it read **1.0 on a question that scored 0.7** (sumgrades 0.7 while maxfraction=1.0). The per‑question mark = **last step's fraction** in `mdl_question_attempt_steps` (max `sequencenumber`) × `qat.maxmark`. The student's actually‑submitted code = **`mdl_question_attempts.responsesummary`** (the step_data `responsesummary` rows are empty on the final step — don't use them for the final answer). ## "How many students did / didn't do quiz X" (excl. helpers)

Recurring class of question ("how many students have started/not done quiz X, excluding helpers"). Verified working query (2026-09-09, course <cid>, E-Quiz 1 id 57 / Demo CE-Quiz id 56):

```sql
SELECT COUNT(DISTINCT ra.userid) AS students_total,
       COUNT(DISTINCT CASE WHEN qa.id IS NOT NULL THEN ra.userid END) AS students_started,
       COUNT(DISTINCT CASE WHEN qa.state = 'finished' THEN ra.userid END) AS students_finished,
       COUNT(DISTINCT CASE WHEN qa.state = 'inprogress' THEN ra.userid END) AS students_inprogress
FROM mdl_role_assignments ra
JOIN mdl_user_enrolments ue ON ue.userid = ra.userid
JOIN mdl_enrol e ON e.id = ue.enrolid AND e.courseid = <courseid>
LEFT JOIN mdl_groups_members gm ON gm.userid = ra.userid AND gm.groupid = <helpergid>  -- 'helpers' group in course <cid> (verify via mdl_groups)
LEFT JOIN mdl_quiz_attempts qa ON qa.userid = ra.userid AND qa.quiz = <quizid>
WHERE ra.roleid = (SELECT id FROM mdl_role WHERE shortname = 'student')
  AND ra.contextid = (SELECT id FROM mdl_context WHERE contextlevel = 50 AND instanceid = <courseid>)
  AND ra.component = 'core'
  AND gm.id IS NULL;
-- not done = students_total - students_started
```

- **"Student" = course-level student role** (level-50 context, pitfall 7), not bare enrollment: `COUNT(*)` over `mdl_user_enrolments` joins returned 237 for course <cid> (staff + auto-provisioned LTI accounts included) vs 205 student-role users — the enrollment number silently inflates denominators.
- **Group id 89 is course-3-specific** — always confirm the group's id/name with `SELECT id, name FROM mdl_groups WHERE courseid = <cid> AND name = 'helpers'` rather than trusting the number across semesters.
- "Started" = has any `mdl_quiz_attempts` row (any state); "finished" = `state = 'finished'` (state values: `inprogress`, `finished`, `aborted`).
- **Attempts include non-staff-role users too:** the raw `mdl_quiz_attempts` join to `mdl_user` also captures **teachers/teaching staff** (e.g. a non-editing teacher enrolled via LTI in course <cid>). Teachers are **exempt from quiz time limits and time windows**, so a teacher's attempt may sit `inprogress` for many hours or even days across the quiz window — do NOT flag that as anomalous (verified 2026-09-14: <student-A>, uid 726, non-editing teacher, 15+ h in-progress on CE-Quiz 1). When interpreting a long in-progress attempt, check the user's role (`mdl_role_assignments` at the level-50 course context) before calling it suspicious; for "how many STUDENTS attempted" use the student-role-scoped query above, which excludes them automatically.
- User wants **counts only, no names/ids**, and helpers excluded by default in this question class.

## "List students who scored ≤X% on quiz Y" (score reports)

**Scale trap — read first:** `mdl_quiz_attempts.sumgrades` (note: `sumgrades`, not `sumgrade`) is on the **question-mark scale**, which is usually **NOT** `mdl_quiz.grade` (the gradebook display max). E-Quiz 1 (course <cid>, id 57): question total = **22**, `mdl_quiz.grade` = **80**. Dividing `sumgrades` by 80 gives garbage (a 20/22 student reads as 25%, not 91%) — on 2026-09-14 this first produced the absurd report "all 186 submitters are ≤30%".

Authoritative % = **the gradebook**: `mdl_grade_grades.finalgrade` on the quiz's `mdl_grade_items` row (`itemmodule='quiz'`, `iteminstance=<quizid>`), rescaled to `mdl_quiz.grade`. Caveats:
- The grade item's `maxgrade` is often **NULL** on this site (verified 2026-09-14: all 40 course-3 quiz items are NULL) — do NOT compute the threshold as `0.3 × item.maxgrade` (0.3 × 0 = 0 → zero rows, looks like "nobody ≤30%"). Use `mdl_quiz.grade` for the threshold.
- `finalgrade` NULL/'' = no computed grade (not submitted, or grade sync pending) — **not** a zero. `finalgrade = '0.00000'` is a genuine zero score (2026-09-14 cross-check: the 5 students with raw 0/22 were exactly the 5 gradebook `0.00000` rows).

Cross-check technique: derive the true question max from any one correct grade pair — `actualmax = sumgrades / (finalgrade / quiz.grade)` (e.g. 8 / (29.09091/80) = 22.0). Then raw % = sumgrades / actualmax, and the raw ≤X% set must match the gradebook ≤X% set. Per-question drill-down: `mdl_question_attempts` keys off `questionusageid` here (no `attempt` FK) and its marks column is `maxmark` (not `maxgrade`); `mdl_question_usages.id == mdl_quiz_attempts.uniqueid` (pitfall 16).

```sql
-- graded students, lowest first (NULL/'' = not yet graded, listed last)
SELECT u.lastname, u.firstname, u.email, g.finalgrade
FROM mdl_grade_grades g
JOIN mdl_grade_items gi ON gi.id = g.itemid
JOIN mdl_user u ON u.id = g.userid
WHERE gi.itemmodule = 'quiz' AND gi.iteminstance = <quizid>
ORDER BY (g.finalgrade IS NULL OR g.finalgrade = '') DESC,
         CAST(g.finalgrade AS DECIMAL(10,2)) ASC;
-- <=X% filter: g.finalgrade <= (SELECT grade FROM mdl_quiz WHERE id = <quizid>) * 0.30
```

"Has not submitted" = no non-preview `state = 'finished'` attempt — use the student-role-scoped query from the section above (it also excludes helpers/test accounts; see pitfalls 22/24 for the roster of test emails).
